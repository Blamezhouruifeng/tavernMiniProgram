## 0. 阅读说明

### 0.1 优先级定义

| 标记 | 含义 |
|---|---|
| **P0** | 首版（M1）必须完成，缺一项业务跑不起来 |
| **P1** | 第二版（M2），复购与留存 |
| **P2** | 第三版（M3），精细化运营与差异化 |
| ★ | 容易被漏掉、但真实开店必然撞上的点 |

### 0.2 角色定义

| 角色 | 说明 |
|---|---|
| 客人（C 端） | 微信用户，扫码进桌点餐；可能未注册、未绑手机 |
| 桌友（C 端） | 同一次桌台会话内的其他客人，参与共享点单 |
| 店员（S 端） | 服务员 / 吧台 / 后厨 / 店长。**与客人共用同一个小程序**，登录工作账号后按角色进入「工作台」视图 |
| 店长 / 老板（B 端） | 后台管理，看报表、配菜单、管权限 |

### 0.3 核心术语

| 术语 | 定义 |
|---|---|
| **营业日** | 从本店开市时刻起算的 24 小时，可跨自然日（如 18:00–次日 03:00 算同一营业日）。**所有营收报表以此为准** |
| **开台 / 桌台会话** | 一次完整的「一桌客人从落座到离开」。整桌唯一 ID，是共享点单、桌账单、存酒归属的主干 |
| **清台 / 关台** | 桌台会话结束、归档，桌位释放为「空闲」 |
| **先付制** | 客人必须先完成支付，订单才进入制作流程；未支付订单一律不出票、不制作、不占库存 |
| **行级状态** | 订单明细行自己的制作/上菜状态（与整桌、整单分离） |
| **桌账单** | 一次桌台会话内所有已付订单的聚合视图（仅供查看 / 开票 / 取证，不是一笔支付） |
| **代存 / 购酒寄存** | 客人自带酒水登记寄存，或店内购酒未喝完寄存 |
| **退酒入存** | 已付款的整瓶酒，客人当场决定不喝完，直接转为存酒记录 |
| **转赠** | 把存酒份额转让给其他会员，凭领取链接 + 手机号领取 |
| **弃酒** | 存酒超期后按规则处置（自动续期 / 转积分 / 报损） |

## 1. 产品定位与前提假设

- 单店起步，**所有业务表预留 `store_id`**，后续多店不改结构。
- **先付制**：扫码 → 点餐 → 支付 → 立即制作 → 上桌（无店员接单环节）。
- 就餐形态：堂食为主，酒水**默认仅堂食**，外带能力可选配置。
- 一桌多人独立下单，**全桌点单内容互相可见**（硬需求）。
- 存酒是本产品核心留存钩子，分为「代存」与「购酒寄存」两种来源。
- 后端复用 HotGo 已有能力：会员、权限(casbin)、支付网关、消息队列、WebSocket、日志、代码生成。

### 2.1.1 一套会员体系，两种视图（架构约束 · 已确认）

**结论**：客人端与店员端**是同一个微信小程序**，且**共用同一套会员体系**——全店只有一个身份池：会员。不申请第二个小程序，不建独立员工账号体系。

#### 身份与开通方式

| 项 | 说明 |
|---|---|
| 身份载体 | **会员**（HotGo 会员体系）。无论客人还是员工，都是同一条会员记录 |
| 店员资格 | 后台在会员记录上勾选「**是员工**」并分配**员工角色**（服务员/吧台/后厨/店长）→ 该会员即获得工作台权限 |
| 视图判定 | 小程序启动 / 每次进前台时调 `GET /member/profile` 取会员态，按 `is_staff` 决定初始视图：`false` → 客人视图；`true` → 工作台 |
| 取消资格 | 后台取消「是员工」或停用账号 → 下次进入自动回落客人视图，历史会话令牌失效 |

#### 视图切换

| 触发 | 进入 | 说明 |
|---|---|---|
| 普通会员打开小程序 / 扫桌码 | 客人视图 | 默认，无需任何登录动作 |
| 员工会员打开小程序 | **自动跳转工作台** | 凭已登录的会员身份直接进入，**不需要再输一套账号密码** |
| 工作台内「切换为客人视图」 | 客人视图 | 员工本人也可正常消费与点单 |
| 客人视图中扫**员工码** | 重试身份判定并跳转工作台 | 仅作兜底（换手机、登录态丢失、门店共用设备换人） |

#### 路由与页面组织

```
uniapp/src/
├── pages/                # 客人主包页面（首页/菜单/购物车/订单/会员…）
├── subPages/             # 客人分包页面（存酒/优惠券/评价/预订…）
├── pagesStaff/           # 工作台主包页面（待办/桌台看板/出票区…）★ 新增
└── subStaff/             # 工作台分包（核销/盘点/日结/异常…）★ 新增
```

- 工作台做成**独立分包**，客人正常点餐不会加载这部分代码（控主包体积、加快首屏）。
- 页面必须在 `uniapp/pages.config.ts` 注册（该文件为页面唯一来源，`pages.json` 是生成物）。

#### 权限模型（三层，缺一不可）

1. **前端守卫**：按 `is_staff` + 角色决定可进入的页面；无权限直接回落客人视图。
2. **后端鉴权**：工作台接口走独立路由分组 + 中间件（如 `/admin/tavernStaff/**`），校验 `会员登录态 + is_staff + 角色(casbin)`；**不允许**仅靠前端隐藏。
3. **操作审计**：工作台每个写操作（出票、核销、沽清、退款、免单、强制释放会话）记录 `member_id + 角色 + 时间 + 桌台会话`。

#### 必须注意的冲突点

| 冲突 | 处理 |
|---|---|
| 员工本人也是消费者，**台账会混同** ★ | 审计日志记录 `member_id + 角色`；员工被取消资格后历史操作记录仍可追溯；报表区分「员工消费」与「客单」（可选：给员工会员打标签，便于内部核对） |
| 员工离职 | 后台取消「是员工」+ 停用会员 → 立即失去工作台（比双账号体系更省事） |
| 会员注销 | 注销前必须先取消员工资格，避免注销后仍持有工作台权限 |
| 门店共用设备换人 | **已定：方案 A + 员工码兜底** —— 工作台内「退出登录」清掉会员登录态，换人后重新微信登录；若登录态异常则扫员工码重走身份判定。不做「设备临时换绑他人会员」 |
| 店员手机丢失 | 后台**强制下线** + 临时取消「是员工」 |
| 工作台消息通道 | 与客人视图共用会员订阅消息，但工作台内要有独立红点/提示，不依赖客人页面栈 |
| 小程序审核 | 单一小程序按"餐饮服务"类目提交；客人视图不出现员工入口文案 |
| **员工码被拍照外传** | 员工码只是「入口」不是「凭证」：扫到也只对已具备员工资格的会员有效；仍支持后台一键作废重生成 |

## 3. 关键状态机

### 3.1 订单（先付制：支付即制作，无接单环节）

```
提交订单【待支付 pending_pay】
   ├─ 微信支付成功 ──► 【制作中 making】──►【已上齐 served】──►【已完成 finished】
   │                     ↓（自动：写支付信息、扣库存、出票、推订阅消息、落对账）
   ├─ 超时未付（默认 5 分钟）──►【已取消 canceled】自动释放库存
   └─ 客人主动取消（未支付）──►【已取消 canceled】
退款：制作前可自助原路退 / 制作后店员审核 → 【退款中 refunding】→【已退款 refunded】
```

三条独立流水线字段（**不得合并成一个 status**）：

| 字段 | 取值 |
|---|---|
| `pay_status` | `unpaid / paid / partial_refund / refunded` |
| `making_status` | `making / served / finished` |
| `refund_status` | `none / applying / approved / rejected / done` |

### 3.2 桌台会话

```
空闲 idle ──开台──► 用餐中 open ──清台──► 已归档 closed
                      │  （期间可换台/并台，订单随之迁移）
                      └── 全部订单完成 + 店员点清台 → closed
```

### 3.3 存酒

```
在库 stored ──取酒核销──► 部分取出 / 已取完 taken
      ├──转赠──► 已转让 transferred
      ├──超期──► 已过期 expired ──处置──► 续期 / 转积分 / 报损
      └──异常──► 报损 damaged / 丢失 lost
```

## 4. 关键业务规则（写死为"必须"，不做成口头约定）

1. **未支付订单不进后厨、不制作、不出票**；支付成功回调是唯一入口。
2. **提交订单时预占库存，支付回调原子实扣**；扣不到自动全额原路退款。
3. **行级制作状态**：每道菜独立标记，禁止整单粗暴置为"已上齐"。
4. **全桌点单可见**：同会话所有人可看全部已点内容与制作状态。
5. **归属不可越权**：只能操作自己下单的行；不能修改他人购物车行。
6. **提交只清已付的行**，他人购物车行保留。
7. **加菜必须重新支付**，桌台会话不因此关闭。
8. **同一菜品多次下单各自成行，不做合并去重**（那是两份，不是重复）。
9. **支付前可自助取消**（限未制作），制作后必须店员审核。
10. **退款必须原路退回**，不得线下转账；对账以微信账单为准。
11. **存酒仅支付成功的订单可入台账**；退酒入存必须联动撤销/扣减。
12. **存酒取酒需手机号 + 动态取酒码 + 店员确认**，三者缺一不可。
13. **营业日口径用于所有营收统计**（可跨自然日）。
14. **所有改价、免单、退款、报损、核销、强制释放会话必须留操作人痕迹**。

## 8.1 开发顺序（已确认）

**前端先行 + 契约先行**：先用「与后端路径一致的 mock」把小程序端完整跑通（点餐 → 共享桌台 → 提交 → 支付 → 制作进度 → 存酒），同时把接口契约固定下来；后端再按同一份契约实现，切换 `VITE_API_BASE_URL` 并关闭 mock 即打通。

理由：产品体验仍有调整空间，先出可点的真机效果能更快收敛需求；且 HotGo 后台能力已具备，后端可延后。

风险与兜底：
- **支付**、**库存并发**、**回调幂等** 三项必须在后端实现，mock 仅用于前端自证，不作为验收依据。
- 制作进度 mock 为了演示，把「预计制作分钟数」当作秒推进。
